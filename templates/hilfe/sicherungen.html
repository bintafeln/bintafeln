Der Server sichert Datenbank und hochgeladene Dateien verschlüsselt. Lesen kann die Sicherungen nur, wer den privaten Sicherungsschlüssel hat; der liegt nicht auf dem Server. Menü: „Einstellungen → Sicherungen“.

Jetzt sichern

Bei jedem Auftrag steht „Jetzt sichern“. Das geht immer, auch wenn der Zeitplan des Auftrags ausgeschaltet ist. Die Sicherung startet nach wenigen Sekunden; die Seite zeigt „läuft …“ und danach das Ergebnis.

Sicherungsaufträge

Ein Auftrag legt fest:

  • Ziel: der Sicherungsordner des Servers oder ein externes Medium, z. B. eine USB-Platte oder ein Netzlaufwerk (NAS). Zur Auswahl stehen alle Ordner, die auf dem Server unter /media oder /mnt eingehängt sind, mit freiem Platz. Eine gerade angesteckte Platte erscheint spätestens nach 30 Minuten. bintafeln legt dort einen Ordner „bintafeln“ an.
  • Wochentage und Uhrzeit, z. B. täglich 02:30 oder sonntags 22:00.
  • Aufbewahrung: höchstens so viele Stände und/oder so viele Tage. Ältere Stände werden gelöscht, die neueste Sicherung bleibt immer.
{% hilfe_bild "sicherungen-auftrag" "Neuer Auftrag: ① Ziel wählen (z. B. eine USB-Platte), ② Wochentage, ③ Uhrzeit, ④ wie viele Stände bleiben." %}

Je Ziel gibt es einen Auftrag. Der Auftrag „Tägliche Sicherung auf dem Server“ ist immer da: Dorthin sichert auch das Update, und von dort wird wiederhergestellt. Er lässt sich ausschalten, aber nicht löschen.

Eine Sicherung nur auf dem Server schützt nicht vor einem Defekt des Servers. Am besten zusätzlich auf ein externes Medium sichern, das an einem anderen Ort liegt oder regelmäßig getauscht wird.

Sicherung außer Haus (Fernablage)

Weil die Sicherungen bereits verschlüsselt sind, kann man sie bedenkenlos auf einen fremden Speicher legen – dort sieht niemand den Inhalt. Unter „Sicherung außer Haus“ auf der Sicherungsseite richtet man eine Fernablage ein; danach lässt sie sich bei einem Auftrag als Ziel wählen. Man muss nichts über die Technik dahinter (rclone) wissen: Oben die Art wählen, dann erscheinen genau die passenden Felder, und bintafeln setzt den Rest selbst zusammen. Die Zugangsdaten werden verschlüsselt gespeichert und aus Sicherheitsgründen nicht wieder angezeigt – ein leeres Passwort-Feld beim späteren Bearbeiten heißt „unverändert“.

Was in die Felder gehört, je nach Art:

  • SFTP (SSH-Server / Storage Box): Sichern über eine SSH-Verbindung, z. B. auf eine Hetzner Storage Box. Nötig sind Server (z. B. u123456.your-storagebox.de), Benutzername und – zur Anmeldung – entweder ein Passwort oder eine Schlüsseldatei (nicht beides). Der Port ist üblicherweise 22 (bei Hetzner-Storage-Boxen oft 23) und kann leer bleiben, wenn es der Standard ist.
    • Mit Passwort: einfach das Passwort des SSH-Zugangs eintragen – sonst nichts.
    • Mit Schlüsseldatei (empfohlen, sicherer): Ein SSH-Schlüsselpaar besteht aus einem privaten und einem öffentlichen Schlüssel. Den privaten Schlüssel (die Datei, z. B. id_ed25519 – ohne Passphrase) laden Sie hier hoch. Den dazugehörigen öffentlichen Schlüssel (id_ed25519.pub) hinterlegen Sie beim Anbieter bzw. auf dem Zielserver (bei einer Storage Box im Kundenmenü unter „SSH-Keys“, sonst in der Datei ~/.ssh/authorized_keys des Zielbenutzers). Erzeugt wird so ein Paar z. B. mit ssh-keygen -t ed25519 -N "". Ein Passwort ist dann nicht nötig. Eine bereits gespeicherte Schlüsseldatei lässt sich über das Häkchen wieder entfernen.
  • Nextcloud / ownCloud / WebDAV: Anbieter wählen, dann die WebDAV-Adresse. Bei Nextcloud/ownCloud hat sie die Form https://cloud.example.de/remote.php/dav/files/BENUTZER/ (BENUTZER durch den eigenen Anmeldenamen ersetzen). Benutzername ist der Anmeldename. Als Passwort am besten kein normales Login-Passwort nehmen, sondern ein eigens angelegtes App-Passwort (in Nextcloud: Einstellungen → Sicherheit → „App-Passwort erstellen“); das lässt sich jederzeit zurückziehen, ohne das Hauptpasswort zu ändern.
  • S3-kompatibel (Backblaze B2, Wasabi, Hetzner Object Storage, MinIO …): Anbieter wählen, dann Access Key ID und Secret Access Key eintragen – die bekommt man beim Anbieter beim Anlegen eines „Application Key“ / „Access Key“. Bei allen außer Amazon AWS zusätzlich den Endpunkt (z. B. s3.eu-central-003.backblazeb2.com, steht in der Bucket-Übersicht des Anbieters); bei Amazon AWS bleibt er leer, dort genügt die Region. Der Bucket/Container muss beim Anbieter bereits existieren.
  • FTP / FTPS: Server, Benutzername und Passwort wie beim FTP-Zugang; Port üblicherweise 21. Wenn der Anbieter es unterstützt, das Häkchen „Verschlüsselt (FTPS)“ setzen – sonst gingen die Zugangsdaten unverschlüsselt über die Leitung.
  • Experten: Für Sonderfälle (z. B. Google Drive, OneDrive) lässt sich stattdessen ein fertiger rclone-Block einfügen; er muss mit [fern] beginnen.

Wichtig: Der private Sicherungsschlüssel (mit dem die Sicherungen verschlüsselt sind) gehört nicht auf denselben Fremdspeicher – ohne ihn nützt die Fernsicherung nichts, mit ihm neben den Daten wäre der Schutz dahin. Ihn getrennt aufbewahren (siehe ./betrieb schluessel).

Wenn etwas nicht stimmt

  • „Fehlgeschlagen“ auf der Startseite: Die Meldung nennt den Grund, z. B. „Ziel nicht erreichbar“ (Platte nicht angesteckt) oder ein volles Ziel.
  • „Der Sicherungsdienst meldet sich nicht“: Auf dem Server docker compose up -d; die technisch verantwortliche Person sieht Details mit docker compose logs backup.
  • Kein Sicherungsschlüssel: Auf dem Server einmal ./betrieb schluessel ausführen.

Wiederherstellen

Wiederherstellen erledigt die technisch verantwortliche Person auf dem Server mit ./betrieb wiederherstellen NAME und dem privaten Schlüssel. Stände von einem externen Medium vorher in den Sicherungsordner des Servers kopieren.
